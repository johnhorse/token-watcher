# v0.2 成本估算（Cost Estimation）设计规约

> 状态：定案（经 Codex & agy 双模型第二意见审查与工程加固）  
> 日期：2026-10-20  
> 目标版本：v0.2.0  
> 前置标准：token-watcher-design-v1.1.md（路线图第 3 位）、Meter Face 诚实仪表美学（45° 斜线纹理）

---

## 1. 为什么需要成本估算

在 v0.1 与 v0.2 前期版本中，Token Watcher 实现了精准的 Token 数量计量（输入、输出、缓存写入、缓存读取）以及请求级本地代理归因：
- **用户痛点**：开发者高频使用 Claude Code 时对抽象的「Token 计数」缺乏直观的金额感知。不同模型单价差距极大（例如 Claude 3 Opus 输出 $75/MTok vs Claude 3.5 Haiku 输出 $4/MTok，差距近 19 倍；Cache Read 仅为基础输入单价的 1/10）。单看 Token 总量极易失真。
- **多中转用户痛点**：使用 CC Switch 在 Anthropic 官方、DeepSeek、各大中转之间切换的用户，各个订阅档案的支出总额需要一目了然地汇总核对。
- **诚实仪表美学原则（Meter Face）**：
  - 成本计算天然是**估算**（第三方中转折扣、计费汇率、历史优惠等无法从本地日志 100% 还原）；
  - Token Watcher 恪守「表只报告，不训人」与「诚实编码」：所有成本金额展示必须使用已有的 **45° 斜线纹理（`.hatch`）** 标明为估算，绝不与物理测量 Token 混淆；
  - 遇到未知中转或私有模型时，**绝不假定为 $0 免费**（防止虚假降低总额），必须诚实显示实际已知成本 + `*` 标识，并标注未定价 Token 数量与占比。

## 2. 双模型第二意见工程加固项（P0 ~ P2）

经由 Codex 与 agy 联合深度审查，针对原草案的 2 项 P0、5 项 P1 与若干工程细节作出统一裁决与加固：

### 2.1 P0 加固裁决

1. **缓存单价与缺省规则明确化（P0-1 加固）**：
   - 若模型条目中 `input_cost_per_token` 缺失或非有限数，整模型直接视为 **未定价（Unpriced）**，严禁进行猜算推导；
   - `cache_read_input_token_cost` 缺失时：若为 Anthropic 家族模型，按 `input_cost * 0.1` 估算；若为非 Anthropic 模型，默认退化为 `input_cost`（即不打折，不凭空捏造未证实的读折扣）；
   - `cache_creation_input_token_cost` 缺失时：Anthropic 家族模型按 `input_cost * 1.25` 计算；**非 Anthropic 家族模型一律记为 0.0**（严禁将 Anthropic 专有的 1.25× 写入溢价套用至 OpenAI/DeepSeek/GLM 等无写入溢价的提供商）。
2. **拒绝硬编码旧日期快照，采用动态最新 key 匹配（P0-2 加固）**：
   - 针对 `claude-sonnet`、`claude-opus`、`claude-haiku` 等裸家族名称，严禁硬编码过期日期；
   - 匹配引擎在加载价格表时，自动维护各家族的「最新日期候选索引」（按日期后缀字典序降序排序）；裸别名统一自动解析至该家族当前可用的最新稳定版本；
   - 严禁将不同定价层级的模型相互归并（例如严禁将 `deepseek-flash` 强行映射到 `deepseek-chat`），未在表中显式定义单价的私有层级模型一律诚实 fallback 到 **未定价（Unpriced）**。

### 2.2 P1 加固裁决

3. **扩展 SQL 聚合查询以支持四项 Token 分解（P1-1 & P1-3 加固）**：
   - 现有 `models_between` 仅有 `SUM(r.input + r.output + ...) AS tokens`，无法乘以四项不同单价；
   - 升级 SQL 查询，聚合出各模型的四项独立统计：`SUM(r.input), SUM(r.output), SUM(r.cache_read), SUM(r.cache_creation)`；
   - 同理，`profiles_between` 扩充 `GROUP BY r.profile_id, r.model` 或在同次查询中完成档案级别的模型细分，以精确计算每个 Profile 卡片的估算金额与覆盖率；
   - 由于引入了浮点型成本字段，相关结构体（`ModelSlice`、`ProfileCard`、`Dashboard`）的派生标记从 `Eq` 调整为 `PartialEq`。
4. **除以零与浮点安全保证（P1-2 & P1-5 加固）**：
   - 当 `total_tokens == 0`（空时间段或无数据）时，显式设定 `coverage = 1.0, is_complete = true, total_cost = 0.0`，彻底阻断 `0/0 -> NaN` 污染 JSON；
   - 严禁使用浮点 epsilon 判断完整性；以整数 `unpriced_tokens == 0` 作为唯一的 `is_complete` 判定真值；
   - 所有序列化边界做 `f64::is_finite()` 守卫，异常值自动归零。
5. **LiteLLM Schema 容错与全量表健康保护（P1-7 加固）**：
   - 容错反序列化：`#[serde(default)]` + 忽略所有未知元数据字段；
   - 脏值丢弃：单条条目若价格出现负数、NaN、或为非模型通配符则丢弃该条，绝不中断全文件解析；
   - 整体健康度检查：若远程下载解析出的有效模型条目数 `< 1000`，判定为格式断裂或损坏，**自动保留现有磁盘缓存与内置兜底**，绝不将坏表换入内存。

### 2.3 P2 性能与并发纪律

6. **锁纪律与启动流程**：
   - 内存使用 `Arc<RwLock<PriceTable>>`；IPC 查询只在临界区内按需提取单价数组 `[f64; 4]`，**绝不跨异步边界持锁**；
   - 启动时**同步读取**磁盘缓存或内置兜底，确保首帧 `get_dashboard` IPC 立即获得价格数据；后台定时器仅负责无阻塞异步拉取与写盘；
   - 价格表成功更新后，由 Tauri 发出 `pricing-updated` 事件，通知前端刷新当前仪表盘。
7. **视觉与格式化标准**：
   - 直接复用 `ui/src/theme.css` 中现有的 `.hatch` 样式类；
   - 金额格式化规则（USD）：
     - `>= $10.00`：保留两位小数（如 `$14.25`）；
     - `$0.01 ~ $9.99`：保留两位小数（如 `$1.45`）；
     - `< $0.01` 且 `> 0`：显示 `<$0.01`（Tooltip 提供完整高精度 `$0.0034`）；
     - `== 0`：显示 `$0.00`；
   - 免费模型（单价为 0）正常计算并计入已定价 Token，不打 `*` 标识。

## 4. 数据契约定义

### 4.1 Rust 核心契约 (`src-tauri/src/core/agg.rs`)

```rust
#[derive(Debug, Clone, Copy, PartialEq, Serialize, Deserialize, Default)]
pub struct TokenCost {
    /// 估算总花费（美元 USD）
    pub total: f64,
    /// 覆盖率（0.0 ~ 1.0）
    pub coverage: f64,
    /// 是否全额已定价 (unpriced_tokens == 0)
    pub is_complete: bool,
    /// 未定价 Token 数量
    pub unpriced_tokens: i64,
}

#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
pub struct ModelSlice {
    pub model: String,
    pub tokens: i64,
    /// 单模型估算花费（美元），None 表示该模型未定价
    pub cost: Option<f64>,
}

#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
pub struct ProfileCard {
    pub profile_id: Option<i64>,
    pub display_name: String,
    pub endpoint: Option<String>,
    pub inferred: boolean,
    pub tokens: TokenTotals,
    pub quota: QuotaInfo,
    /// 档案总估算花费
    pub cost: Option<TokenCost>,
}

#[derive(Debug, Clone, PartialEq, Serialize, Deserialize)]
pub struct Dashboard {
    pub range: Range,
    pub totals: TokenTotals,
    /// 总体估算花费
    pub cost: TokenCost,
    pub pulses: Vec<UsagePulse>,
    pub models: Vec<ModelSlice>,
    pub profiles: Vec<ProfileCard>,
    pub sessions: Vec<SessionRow>,
}
```

## 5. 验收标准与验证方案

1. **单价与聚合准确性**：
   - 单元测试：已知模型（如 `claude-3-5-sonnet-20241022`、`deepseek-chat`）按四项 token 精准累乘，验证精度在 1e-6 以内；
   - 空记录防御：无记录时 `total = 0.0, coverage = 1.0, is_complete = true`，无 NaN；
   - 混合模型：含 1 个已知模型与 1 个未知私有模型时，已知模型正确计费，未定价 token 被正确累加，`is_complete = false`；
2. **离线与故障韧性**：
   - 离线/断网环境下启动，内置价目表正常工作，常见模型定价完整；
   - 远程文件损坏或 < 1000 条条目时，保留磁盘旧表，不崩溃、不覆盖；
3. **UI 视觉表现**：
   - 总额与各模型展示估算金额，带 `.hatch` 45° 斜线背景纹理；
   - 存在未定价 token 时，清晰展示 `*` 号与未定价数量提示。
