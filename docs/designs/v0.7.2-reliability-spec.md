## Problem Statement

用户提出「能否实时监测」。澄清后真实需求是**完成即达**：一次请求完成后数秒内反映到 token-watcher，不追求生成中的流式可见。伴随两个实证问题：

1. **体感漏更新**（「有时候一连几轮请求都没有更新」）：全量对账证实当前 omp 管道无漏（145 个会话文件 11806 行 usage，仅 1 条缺失且为 10-21 修复切换窗口战损，其余全部入库）。但确认过程暴露两个结构性缺口：
   - 无日志：`eprintln!` 在 GUI 下进黑洞，间歇性问题无法事后取证；
   - 无兜底：主循环 `next_deadline()`（watch.rs:808）空闲时无限阻塞，fs 事件被吞即失明；且 `collect_dir_sources` 会跳过落在监听根自身的目录事件（正是 FSEvents MustScanSubDirs 溢出提示的落点）。
2. **exec/-p 一次性调用盲区**：`claude -p` 与 `codex exec` 落盘且已记录（codex_exec 入口 1051 条）；但 `omp -p` print 模式 transcript 不落盘（实测两次运行零文件、session 以 dispose 退出），omp provider 直连 API（如 google-antigravity → Gemini API）任何地方都不落盘。文件监测对这类流量物理不可见。

## What Makes This Cool

- 「感觉没更新」从 40 分钟人肉对账变成 30 秒 `audit.py` 快检；
- 兜底重扫把「被吞的 fs 事件」从静默丢数据变成自愈重读，可靠性不再依赖运气；
- v0.8 计量代理（metering bridge）让「不落盘的 token 消耗」第一次有解：代理即电表，任何 OpenAI/Anthropic 兼容客户端接上就被计量。

## Constraints

- SC6 空闲 CPU≈0：兜底轮询在空闲期放宽为 60s 毫秒级轻量 stat（精神不变，字面从「零轮询」放宽）；
- 包体约束：不引入新 crate，日志器手写（约 50 行）；
- 单写者纪律：不新增线程、不并发写 SQLite；
- 口径诚实：任何部分口径数据必须显式标注（拒绝 model_perf 差值法正因此）。

## Premises（全部经用户确认，含 Codex 冷读修订）

1. **P1 日志**：`~/.token-watcher/log/` 滚动日志，默认约 2MB×2、体积可配；info 级只记路径与计数（事件判定、flush 批次、checkpoint 推进、轮询动作），不记消息内容/token 明细/密钥；零新依赖。
2. **P2 对账工具**：`scripts/audit.py`。快检 = 按源类型定义对比基线：JSONL 系（claude/codex/omp/zcode/qoder/workbuddy 及 aider 的 analytics.jsonl）当前 size vs byte_offset；OpenCode 源库最新 time_created vs 存储时间戳；Antigravity gen_metadata 最新 idx vs 存储 idx；Cline/Roo/Continue 等记录数型 checkpoint 比对当前 (mtime,size) vs 存储 (mtime,size)；仅 SQLite 源涉及 -wal，且 checkpoint 需旁存 WAL 指纹（size/mtime）作对比基线 → 各类型「未消费增量」报告 + 各引擎 DB 最新时刻；`--deep` = 行级对账，v1 只做 omp + Claude Code；异常退出码非 0。
3. **P3 活跃期兜底重扫**（含修订）：活跃 = 最近 5 分钟内有 fs 事件或新入库记录；活跃期每 3s 执行统一检查矩阵，空闲期 60s 慢扫执行**同一矩阵**（自举悖论兜底：激活信号本身可能被吞）：① JSONL 源（含 aider analytics.jsonl）stat size vs byte_offset；② SQLite 源 stat 主库 + `-wal`/`-shm`（对比 checkpoint 旁存的 WAL 指纹）；③ 记录数型源（Cline/Roo 的 ui_messages.json、Continue 的 *.json）stat (mtime,size)；④ settings.json / codex config.toml stat mtime；⑤ 有界轻扫引擎根目录，按源类型族扫描：JSONL 根用 collect_jsonl_recursive；Cline/Roo 根直接子项的 ui_messages.json；Continue 根下 *.json；Antigravity 根下 *.db（OpenCode 固定 db 路径已由 ② 覆盖）；单轮入队设上限防风暴，覆盖被吞的 Create 事件。**WAL/SHM 增长必须绕过 Antigravity 主库 (mtime,size) 相等短路**（force-read 标志或 WAL 指纹不匹配即强制重读——否则 WAL-only 写入检测到了也读不进来）。参数（5min/3s/60s）实装后可调。
4. **P4 单写者 + 根目录修复**：轮询融进 DataEngine 主循环 `next_deadline`/`on_tick`；目录事件落在监听根自身 → 触发 `needs_catchup`（复用 quiet_scan）。
5. **P5 发版与验收**：随 v0.7.2 发布。验收 = 新增单测五项：根目录事件触发 catchup；无 fs 事件时轮询捡起新增 JSONL 字节；主库不变仅 WAL 增长时也能捡起（须绕过主库短路）；空闲超时后 60s 慢扫捡起新增字节；新源文件无 Create 事件时被根轻扫发现并入账，且至少覆盖一个非 JSONL 源（如 Antigravity 新 .db）+ 本机全量 audit 通过（除已知 10-21 战损外零差异）+ ci-check（fmt/clippy -D warnings）通过。

## Cross-Model Perspective

Codex 冷读（high effort，已采纳）：① High——P3 若只 stat 主文件，SQLite WAL 引擎的兜底是空网（已并入 P3）；② Medium——激活信号源自 fs 事件存在自举悖论，全吞场景仍失明（已并入 P3 空闲慢扫）；③ v0.8 dedup 键必须落到 `(engine, message_id)` 否则双计，SSE 解析按单流假设会被 HTTP/2 多路复用打穿（种子决策点）；④ `stream_options.include_usage` 注入是高杠杆特性；⑤ LiteLLM 可作规格参考（不引入）；⑥ 最酷版本：每引擎三心跳 liveness 地图（fs 事件 / 代理 / DB 记录各自 last-seen，HUD 上陈旧路径亮红标）。被否：HMAC 指纹建议（API key 高熵，SHA-256 前缀不构成字典攻击面，记备忘）。

- **D3-A 到此为止**：否——下次怀疑仍要 40 分钟人肉对账，保险网不封。
- **D3-B 只加日志+audit**：否——可观测性有了，漏事件本身无解。
- **D3-C 全量兜底（选定）**：日志 + audit + 活跃/空闲双层兜底 + 根目录修复。
- **D5-B omp -p 只记 known limitation**：否——方向需要被钉住。
- **D5-C 代理挤进 v0.7.2**：否——与可靠性收尾混发互相拖累（v0.1 Approach A 教训）。
- **D5-A 分步交付（选定）**：v0.7.2 只做可靠性；代理作为 v0.8 种子章节钉死方向。
- **model_perf 差值法**：否——统计口径含全部 omp 用量，与 jsonl 已入账部分双计；整体替换则丢 input/cache/会话归属，违背口径诚实。

## Recommended Approach

**v0.7.2 = 可靠性收尾**，实现顺序采纳 Codex 排序（先改正确性，后加观测）：

1. **T1 (P4)** 根目录事件触发 catchup — `watch.rs` 的 collect_dir_sources / is_*_root 判定分支；verify: cargo test
2. **T2 (P3)** 兜底轮询进主循环 — 活跃判定 + 五项统一检查矩阵（JSONL stat / SQLite 主库+WAL 指纹 / 记录数型 (mtime,size) / 配置文件 mtime / 有界根轻扫）+ 60s 空闲慢扫同矩阵 + WAL 增长绕过主库 (mtime,size) 短路；verify: 五项新单测全绿
3. **T3 (P2)** `scripts/audit.py` 快检 + `--deep`（omp/claude）；verify: 本机全量跑通 + 故障 fixture 退出码非 0
4. **T4 (P1)** 滚动日志器 + 全链路埋点；verify: 手动运行检查日志行
5. **T5** CHANGELOG/版本 v0.7.2 + ci-check；verify: scripts/ci-check.sh

**v0.8 种子：通用计量代理（metering bridge）**

proxy.rs（127.0.0.1:4040，现为 Claude Code 归因桥）升级为计量桥：任何 OpenAI/Anthropic 兼容客户端把 base_url 指向它，从响应 usage 事件计量 4D token 入同一 SQLite。动机：omp -p、provider 直连 API、未来 Cursor/Windsurf 等不落盘流量。关键决策点：
- **防双计**：dedup 键 `(engine, message_id)`，复用 proxy_attributions 晚到对账机制（JSONL 后到时以精确值覆盖/去重）；
- **传输层**：本地监听强制 HTTP/1.1（规避 h2 多路复用串流误归因）；
- **usage 注入**：对 OpenAI 系改写出站请求注入 `stream_options: {include_usage: true}`；
- **活跃心跳**：代理命中即标记引擎活跃并唤醒兜底轮询（独立于 fs 事件的信号源）；
- **/metrics**：OpenMetrics 端点（约 20 行，Grafana/Prometheus 可抓取）；
- **key 安全**：沿用指纹不存原文；HMAC+盐作为可选加固备忘；
- **关联身份验证（v0.8 前置调研项）**：代理侧 API 响应 id ↔ 文件侧 record 身份的关联链未经验证（omp 用 transcript 外层 id 或内容哈希、codex 允许无 response id）——立项前须逐客户端验证关联链与 engine 判定，直接使用 (engine, message_id) 可能仍双计；
- **规格参考**：LiteLLM 的 usage 解析边界当 spec 读，不引入；
- **候选延伸**：每引擎三心跳 liveness 地图 + HUD 陈旧红标（data-health 的自然延伸，v0.7.3/v0.8 候选）。

### R3-1 — clarity (minor)

**Problem**

> The new per-family root light scan states an exact depth only for Cline/Roo (「根直接子项的 ui_messages.json」). For Continue (「根下 *.json」) and Antigravity (「根下 *.db」) it never says whether the glob is one level, recursive, or capped like collect_jsonl_recursive's depth filter. If Continue's session files sit one level below whatever this document calls the engine root (e.g. sessions/*.json), a root-level glob finds nothing and a swallowed Create event for Continue stays invisible, silently breaking the very gap ⑤ exists to close.

**Remedy**

> State the exact path pattern and scan depth per non-JSONL family in P3⑤ (e.g. Continue <root>/sessions/*.json; Antigravity recursive *.db with an explicit depth cap) and confirm each newly discovered file is registered as a source and enqueued under the existing per-round cap.

### R3-2 — clarity (minor)

**Problem**

> Matrix item ④ still says only to stat the mtimes of settings.json and codex config.toml; no stored baseline or reaction to a mismatch (re-read immediately, mark settings_dirty for the next flush, refresh the stored mtime) is defined, leaving the poller's settings behavior to implementation.

**Remedy**

> State the stored baseline (e.g., last applied mtime kept in memory or alongside the WAL fingerprint) and that a mismatch schedules the existing settings re-apply path in the next flush instead of re-reading the files on every tick.
