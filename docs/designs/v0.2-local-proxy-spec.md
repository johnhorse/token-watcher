# v0.2 本地代理模式（Local Proxy Mode）设计规约

> 状态：定案（经 Codex 第二意见审查与工程加固）  
> 日期：2026-10-20  
> 目标版本：v0.2.0  
> 前置决策：D23（归因架构倒挂，代理模式提至 v0.2 首位） + P0~P2 Codex 审查处置

---

## 1. 为什么需要本地代理

在 v0.1 中，Token Watcher 依赖监听 `~/.claude/settings.json` 的修改时间线进行**时段推断**归因：
- 当用户在单个终端按时间顺序切换中转时，时间线推断有效；
- **失效场景**（Codex & agy 联合指出的 Critical 缺陷）：
  1. **多终端并发**：终端 A 使用 DeepSeek（通过环境变量 `ANTHROPIC_BASE_URL`），终端 B 使用 Anthropic 官方，时间线无法区分；
  2. **同 URL 多 Key**：两个不同账号或组织使用相同的 base_url，时间线无法区分；
  3. **未知历史**：应用启动前或未产生 settings 变更记录的历史，只能归入 Unknown。

**本地代理模式是彻底解决归因精度的终极方案**：
通过在本地启动轻量 HTTP 反向代理，将 Claude Code 的请求精准截获并转发，在**请求级别**将 `message.id` 与真实的 API Key、Upstream 强绑定，实现 100% 确定性归因。

## 2. 核心架构设计

### 2.1 整体流向与旁路归因桥

```
+-----------------------------------------------------------------------------------------+
|                                  Claude Code 客户端                                      |
|  (推荐: export ANTHROPIC_BASE_URL=http://127.0.0.1:4040；可选: settings.json 注入)         |
+-----------------------------------------------------------------------------------------+
       |                                                                    |
       | HTTP POST /v1/messages                                            | 落盘 JSONL
       v                                                                    v
+-----------------------------------------+                 +-----------------------------+
|    Token Watcher 本地代理 (127.0.0.1:4040)|                 | ~/.claude/projects/*.jsonl  |
|                                         |                 +-----------------------------+
| 1. 解析请求 Header (x-api-key / auth)    |                                |
| 2. 确定 upstream 与档案 (profile_id)      |                                | 文件变更通知
| 3. 流式转发至真实上游 (Anthropic / 中转)    |                                v
| 4. SSE 响应透传，增量行缓冲嗅探 message.id|                 +-----------------------------+
| 5. 向 data-thread 发送 Attribution 消息  |                 |      JSONL Watcher 管道     |
+-----------------------------------------+                 |                             |
       |                                                    | 1. 解析 message.usage        |
       | mpsc channel 统一写者                              | 2. 优先查 proxy_attributions|
       v                                                    |    -> 命中: 100% 精确归因    |
+----------------------------------------------------+      |    -> 未命中: 回退时间线推断 |
|        数据线程 (Watch / Ingest Data Thread)        |      | 3. 幂等入库 usage_records    |
|   1. 写入表: proxy_attributions                    | <----+                             |
|   2. 晚到对账 UPDATE: usage_records                |                                    |
|      (若 JSONL 先到，更新 profile_id 为精确值)     |                                    |
+----------------------------------------------------+                                    |
       |                                                                                  v
       v                                                                    +--------------------+
+----------------------------------------------------+                      | Svelte HUD 界面     |
|              SQLite 数据库 (db.sqlite3)             |                      | 精确档案归因与配额展示 |
|   表: proxy_attributions (message_id PK)           |                      +--------------------+
|   表: usage_records (schema v4: attribution_source)|
+----------------------------------------------------+
```

### 2.2 核心架构决策（P0~P2 加固定案）

1. **单写者与晚到对账（P0-3 处置）**：
   - 代理**绝不直接打开独立的 rusqlite 写入连接**，而是通过已有的 mpsc channel 向数据线程发送 `watch::Message::ProxyAttribution` 消息，完全消除 `SQLITE_BUSY` 风险与 WAL 竞争。
   - Schema v4 为 `usage_records` 新增 `attribution_source TEXT NOT NULL DEFAULT 'timeline'`（取值：`'proxy'`, `'timeline'`, `'manual'`）。
   - **优先级法则**：`manual`（用户手动修正） > `proxy`（代理精确） > `timeline`（时间线推断）。
   - **晚到对账**：当代理记录到达时，不仅写入 `proxy_attributions`，同时执行对账更新：
     ```sql
     UPDATE usage_records 
     SET profile_id = ?, attribution_source = 'proxy' 
     WHERE record_id = ? AND attribution_source != 'manual';
     ```
     彻底解决 JSONL 扫描快于代理入库时的永久锁死失效问题。

2. **生产可用性与故障逃逸（P0-1 处置）**：
   - 本地代理处于付费 coding 的关键链路上，若代理崩溃将导致终端全部请求失败。
   - **连接级隔离**：单个连接的异常、超时或 panic 绝不能导致监听主任务退出。
   - **推荐主路径**：优先向用户推荐终端环境变量复制方式（`export ANTHROPIC_BASE_URL=...`），仅作用于当前终端，随开随走，天然防崩溃蔓延。
   - **安全注入与退出还原**：若用户点击「写入 settings.json」，在 `~/.token-watcher/proxy_injected.json` 记录原始值与时间戳。应用正常退出或下次启动检测到未还原的标记时，自动还原原始 settings.json。

3. **中转路由循环与真实上游持久化（P0-2 处置）**：
   - 若用户配置了第三方中转并点击写入代理，`settings.json` 会被替换为 `127.0.0.1:4040`。若代理此时再去读 `settings.json`，会错误读取到回环地址，进而回退到 Anthropic 官方，导致将中转 key 发送给官方产生 401 或误扣费。
   - **解法**：在注入时将原 `ANTHROPIC_BASE_URL` 持久化到 `~/.token-watcher/proxy_config.json`。
   - **上游解析次序**：
     1. 显式路径档案配置的上游（`/p/<profile_id>/...`）；
     2. `~/.token-watcher/proxy_config.json` 中保存的原配置上游；
     3. 当前 `settings.json` 中的 `ANTHROPIC_BASE_URL`（且必须为非回环地址）；
     4. 默认回退 `https://api.anthropic.com`。
   - **防自转发环路**：若解析出的上游为本机回环地址（`127.0.0.1` / `localhost`）且端口等于代理自身端口，直接返回 HTTP 502 并明确报错，绝不自环。
   - **拒绝 SSRF**：彻底弃用 `x-upstream-url` Header，避免本地恶意进程通过代理探测内网。

4. **增量 SSE 嗅探与响应解压缩控制（P1-5, P1-6 处置）**：
   - 跨 TCP chunk 分包防护：采用行增量缓冲区（Line-based carry buffer），只有遇到换行符才解析 SSE `data:` 行。
   - 从 `message_start` 或顶层 JSON 字段中提取 `id`，通配任何第三方中转的前缀（如 `msg_...`、`chatcmpl-...`），不再硬编码 `msg_`。
   - 代理向真实上游转发请求时，显式设置 `Accept-Encoding: identity`，严禁上游对 SSE 进行 gzip 压缩导致嗅探失效。

5. **时间线自中毒防护（P1-9 处置）**：
   - 在 `attr.rs` 的 `parse_settings` 中，当检测到 `ANTHROPIC_BASE_URL` 为回环地址（`127.0.0.1` / `localhost` / `[::1]`）时，直接返回 `SettingsSnapshot::NoAttribution`，关闭前一区间，不再生成虚假的「本地代理」时间线区间。

## 3. 详细路由与代理行为

### 3.1 监听与端口
- 默认监听：`127.0.0.1:4040`。
- 绑定时使用 `TCP_NODELAY`。
- 若 4040 冲突，自动寻找递增端口并准确向 UI 报告实际绑定的端口（复制命令动态生成，杜绝硬编码）。

### 3.2 路由规则
1. `GET /health`：
   返回 `{"status":"ok","version":"0.2.0","port":4040}`，不泄露上游地址与 Key。
2. `POST /v1/messages` 等模型请求：
   - 剥离逐跳请求头（`Connection`, `Keep-Alive`, `Proxy-Connection`, `Transfer-Encoding` 等）；
   - 替换 `Host` 为真实上游的主机名；
   - 将客户端请求体以 Stream 方式直接流向真实上游（支持超大上下文和图片黏贴，绝不整体 `to_bytes`）；
   - 将真实上游的响应 Chunk 立即透传给客户端，同时分流至行增量嗅探器提取 `message.id`。

### 3.3 凭据指纹与订阅档案识别
- 提取 `x-api-key` 或 `Authorization: Bearer <token>`；
- **OAuth Token 轮换防护（P1-4 处置）**：
  若检测到 token 前缀为 `sk-ant-oat`（Claude Code 轮换订阅凭据），不针对每次轮换生成的随机串单独计算指纹，而是归纳为 `official-oauth` 统一指纹，防止频繁轮换污染数据库；
- 静态 API Key 依然计算 `sha256(key)[0..8]`；
- 档案匹配：根据 `(upstream_endpoint, key_fingerprint)` 在 `profiles` 表中匹配，若不存在则由数据线程自动登记新档案。

## 4. 数据库演进 (Schema v4)

```sql
-- 1. proxy_attributions 旁路表
CREATE TABLE IF NOT EXISTS proxy_attributions (
    message_id TEXT PRIMARY KEY,
    profile_id TEXT NOT NULL,
    upstream_url TEXT,
    created_at INTEGER NOT NULL
);

-- 2. usage_records 增加归因来源跟踪
ALTER TABLE usage_records ADD COLUMN attribution_source TEXT NOT NULL DEFAULT 'timeline';
CREATE INDEX IF NOT EXISTS idx_usage_records_attr_source ON usage_records (attribution_source);
```

## 6. 测试与验收标准

1. **增量 SSE 嗅探测试**：
   - 模拟分包切割（`{"id":"ms` + `g_12345"}` 跨 chunk）测试，确保 100% 正确嗅探；
   - 模拟第三方中转 `chatcmpl-` 风格 ID，验证兼容性；
2. **端到端中继测试**：
   - 启动本地 Mock 上游服务器，客户端走代理调用，验证请求与响应完整性；
   - 客户端提前断开连接时，验证代理及时中止上游请求；
3. **并发对账与防双计测试**：
   - 模拟 JSONL 记录先写入数据库，代理消息后到达，验证晚到对账 UPDATE 生效；
   - 验证用户手动修改为 manual 状态的记录不被代理覆盖；
4. **安全与防自环测试**：
   - 模拟上游指向 `127.0.0.1:4040`，断言返回 HTTP 502 且不卡死；
   - 验证回环 settings 触发 `NoAttribution`，时间线不受污染。
